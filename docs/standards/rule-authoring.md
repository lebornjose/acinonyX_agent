# Harness Rule Authoring Guide

## 规则应该写什么

规则适合约束可验证的工程行为：文件大小、目录职责、导入出口、命名、依赖边界、验证命令和禁止事项。

规则应尽量包含：

1. 适用范围。
2. 强制动作。
3. 禁止动作。
4. 例外条件。
5. 完成后的验证方式。

## 好规则示例

```text
src/utils/ 中的公共方法必须一方法一文件，并且必须从 src/utils/index.js 导出。
新增方法前必须搜索现有 utils，禁止创建重复功能。
```

## 不够明确的规则

```text
代码要保持整洁，公共方法要复用。
```

## 规则优先级

```text
用户本轮明确要求
    ↓
子目录 AGENTS.md
    ↓
根目录 AGENTS.md
    ↓
docs/standards/ 下的统一规范
```

如果用户要求与已有规则冲突，必须明确说明并记录本次例外，不得默默违反规则。
